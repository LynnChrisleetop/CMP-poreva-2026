# 2.10 CLI 与 Agent Skill

> **适用版本**：CLI 长期可用；**Agent Skill 自 v0.3.0 起提供；自 v0.5.12 起 skill 内嵌进 `trisol` CLI 二进制分发，旧的 `npx skills` 安装路废弃；v0.6.0 起 PAT（个人访问令牌）已移除，认证统一走 Vouch 公司统一身份。**

本页是 **鼎曜（Trisol）命令行工具（CLI）与 Agent Skill** 的使用参考：怎么安装 / 更新、怎么登录认证、CLI 能干什么（命令地图 + 权限）、Agent Skill 提供什么、以及怎么把两者配合从零跑通「数据 → 训练 → 部署推理」这条价值链。

鼎曜的设计原则是 **CLI / API 优先**：几乎所有命令支持 `-o json`，响应里 ID 旁边一定带人类可读 name（`team_name` 配 `team_id`、`created_by_name` 配 `created_by`）。所以应当**优先直接用 CLI**；Agent Skill 只在「冷启动多步编排」时帮你省掉人肉查 version / cluster / gpu 的麻烦。

## CLI 与 Agent Skill 的区别

|  | 是什么 | 谁执行 | 怎么装 / 更新 |
|-|-|-|-|
| **`trisol` CLI** | 真正干活的二进制（登录 / 传模型 / 起训练 / 部署推理） | 你或 AI agent 在终端调 | `trisol update` 自更新 |
| **`trisol` Agent Skill** | 一篇编排 playbook，教 AI agent 命令依赖图 + 解析逻辑 | AI agent 读它、按它编排 CLI | 内嵌进 CLI 二进制 —— 装 / 更新 CLI（`trisol update`）即自带；`trisol skill update` 补装 / 修复 |

Agent Skill **不替代** CLI、也**不含**后端逻辑 —— 它就是「知识 + 薄编排」，最终还是调 CLI。

## 安装与更新

### CLI

**首次安装（Linux / macOS）** —— 从鼎曜域名上的 `install.sh` 一键 bootstrap（服务端公开提供，无需登录）：

```bash
curl -fsSL https://trisol.dp.tech/install.sh | bash
```

脚本会探测平台 + 下载匹配的二进制 + 装进 PATH。可选开关（注意 env 要放在 `bash` 一侧，放 curl 前面只作用于 curl）：跳过 skill 安装加 `TRISOL_NO_SKILL=1`；已有配置想强制覆盖加 `TRISOL_OVERWRITE_CONFIG=1`。

**首次安装（Windows 10/11 x86-64）** —— 在 PowerShell 5.1+ 中运行：

```powershell
irm https://trisol.dp.tech/install.ps1 | iex
```

二进制装到 `%LOCALAPPDATA%\Trisol\bin\trisol.exe`，安装器自动更新 user PATH，无需管理员权限。

**后续更新** —— 装好后用 CLI 自更新（从服务端拉二进制，校验 SHA256，原子替换自己，旧版留 `<exe>.bak`）：

```bash
trisol update              # 拉最新 stable
trisol update --check-only # 只比对本地 vs 最新，不下载（落后则非零退出）
```

**首次配置** —— 交互式向导（配 api_url、登录、默认 team、输出格式）：

```bash
trisol init
```

### Agent Skill

自 v0.5.12 起，Agent Skill **内嵌进 `trisol` CLI 二进制分发** —— skill 内容（SKILL.md + references）随二进制一起走公开安装通道，离线可装、版本与 CLI 天然同源。旧的 `npx skills` 安装路自本版本起废弃，不再文档化、也不再支持。

三个触点，任选其一：

- **首次装 CLI 时自动装**：上面的 `install.sh` 在落二进制后会把 skill 写到本地 agent 目录（`~/.agents/skills/trisol/` 为 canonical，再软链进各 agent 目录）。检测到没有已知 agent 消费者（如 `~/.claude` 不存在）会静默跳过，不报错。
- **`trisol update` 联动**：以后每次 `trisol update` 升级二进制，会顺带把内置的 skill 同步刷新到本地（skill 是独立后置步骤，二进制更新成功为准；skill 同步失败只告警，不影响二进制更新结果）。
- **`trisol skill update` 手动补装 / 修复**：跨平台、全程离线的唯一手动入口。install 时跳过了现在想装、skill 目录被删 / 损坏、Windows 用户的主路径、或 agent 按 skill 提示自助刷新，都跑它：

```bash
trisol skill update     # 把当前二进制内置的 skill 写到本地（幂等，首装 = 刷新 = 修复）
trisol skill list       # 查看本地安装状态（canonical 路径 + 软链 + 版本）
trisol skill doctor     # 诊断：CLI 版本 vs 内置 skill 版本 vs 本地安装是否一致，并给出修复命令
```

> **从旧 npx 安装迁移**：之前用 `npx skills add` 装过的机器，直接跑一次 `trisol skill update` 即可 —— 它会把 canonical 目录迁到 `~/.agents/skills/trisol/` 并重建软链；若检测到旧 npx 安装（无我们的 marker），会跳过覆盖并打印迁移指引，按提示删掉旧目录再重跑即可。

> **版本自检（skill 内置）**：skill 每条链路前自动跑，分两步 —— 先用 `trisol version --satisfies <min>` 确认 CLI 够新（太旧会提示你 `trisol update`），再用 `trisol version -o json` 里的 `bundled_skill_version` 和 skill 自身版本比对，skill 旧了提示 `trisol skill update`。纯软提示、绝不阻塞；版本对齐时静默跳过。

## 登录与起步配置

**交互登录（人）** —— `trisol login` 走 **Vouch 公司统一身份**，菜单二选一：浏览器（公司 SSO，默认）或 device code（无浏览器 / 远程 shell）。一次登录经共享 `~/.vouch` state 在所有 Vouch 系 CLI 间复用。`trisol login --status` 查当前登录状态；`trisol logout` 清本地凭据与激活 team——注意它连同共享 Vouch session 一起签出，会影响同机其他 Vouch 系 CLI。

**agent / CI 非交互** —— 环境变量 `TRISOL_TOKEN=<vouch-jwt>`：CLI 的 env bearer 通道（盖过共享 state），不落盘、适合 CI / 容器。JWT 由 mint 流程签发的**短期票**，不要存长期令牌。

> **PAT 已移除（v0.6.0）**：`trp_...` / `trp2_...` 个人访问令牌整体作废 —— 后端一律返回 410 `pat_removed`；CLI 对 `TRISOL_TOKEN` 或旧凭据文件里的 PAT 值在发送前就以同样语义本地报错。CLI 的 `token` 命令族与 Web Profile 页的 Tokens 区已一并删除。旧脚本迁移：人工使用跑 `trisol login`（device code 可无浏览器）；CI / 无人值守自动化改用 mint 流程的短期 Vouch JWT（`TRISOL_TOKEN` 注入），不再存 PAT。

```bash
trisol login                      # 交互认证（device code 可无浏览器）
export TRISOL_TOKEN=<vouch-jwt>   # 非交互认证（agent / CI；mint 签发）
trisol whoami -o json             # 确认身份
trisol config use-team <name>     # 设默认 team（kubectl use-context 惯例）
trisol config set output json     # 默认 JSON 输出（推荐，agent 友好）
```

> **激活 team 很重要**：很多命令（如 `quota list`）只在「目标 team == 激活 team」时走团队成员可读的端点；否则掉到管理员端点，普通用户会在「发现」阶段就失败。要么设激活 team，要么每条命令带 `--team <id|name>`。

**会话体检**：命令返回 401/410 时先 `trisol login --status` 看登录态，过期就重新 `trisol login`。`trisol doctor` 一次看全本地会话状态、server 连通性、CLI 新旧与 skill 安装（`--offline` 跳过网络项，`-o json` 供脚本）——它健康而调用仍失败，问题多半在服务端不在本地会话。

## CLI 命令地图（含权限）

顶层命令组（每组 `trisol <组> --help` 看子命令和 flag）。最后一列是**权限**：日常用户（团队成员）只用得到「普通用户」那批，`cluster` / `admin` / `user` 管理 / 建改配额是平台管理员的事，普通用户用不到。

| 组 | 干什么 | 权限 |
|-|-|-|
| `login` / `logout` / `whoami` / `init` / `update` / `version` / `config` / `completion` / `doctor` | 身份 + CLI 自身（配置 / 自更新 / 版本 / 补全 / 体检） | 任何人 |
| `team` | 团队浏览 + 加入申请 + **批量成员管理**（`team add-members` / `team set-role` / `team remove-member`）+ **调度策略**（`team scheduling`：get / preview / set / status / history / pin，配置见下节） | 任何用户浏览；建团队 / 改成员、保存调度策略需团队或平台管理员 |
| `model` | 模型 CRUD + 多版本 + 上传 / HF 导入 / **下载** + 文件树 | 普通用户（限自己所属 team） |
| `dataset` | 数据集读面：`list` / `get` 读文渊（wenyon）目录薄代理。**写操作已由服务端闸门冻结**（create / upload / import 等一律 400 `legacy_dataset_frozen`，错误体自带文渊引导）——数据集的创建 / 上传 / 管理统一到文渊；`dataset download` 已废止（400 `dataset_download_abolished`），字节下载也走文渊 | 普通用户（限自己 team 可见范围） |
| `train` | 训练 submit / list / get / update / stop / delete / logs / pods / events / wait；`logs` / `events` 用 `--instance` 指定逻辑实例（原 `--pod` 保留为 deprecated 别名，v0.8.1 起） | 普通用户（限自己 team） |
| `inference` | 推理服务 create / list / get / start / stop / update / pods / timeline / token + canary 生命周期（`token` 查看托管推理服务的访问 token，v0.8.1 起） | 普通用户（限自己 team） |
| `leaderboard` | 训练 / 推理用量排名（`training\|inference\|agent-native`） | 任何人 |
| `quota` | GPU 配额 list / get | 普通用户**读自己 team；建 / 改配额是平台管理员** |
| `billing` | 计费目录只读查询：`billing quote --gpu-model <机型> --gpu-count <卡数>` 查该精确规格的当前小时标价（v0.8.1 起） | 任何登录用户 |
| `notify` | 站内信收件箱 | 自己的 |
| `api-keys` | 推理 API Key（给 inference endpoint 调用用，与登录认证无关） | 自己的（限自己 team） |
| `cluster` | 面向成员的可用 GPU 规格查询（`cluster gpu-options`）；集群注册 / 管理 / 同步、托管算力（PAI）的 BMCPFS 存储与网关管理（v0.8.1 起；**管理类子命令 v0.18.0 起迁至 `trisol admin cluster`**） | `gpu-options` 对普通用户开放（限可用团队 / 集群）；管理类命令需**平台管理员** |
| `admin` | 平台管理面：settings（运行时配置）/ framework 审计 / gpu-report / oncall / compute（托管算力域、绑定与凭据）/ runtime-operations（运行时操作检修）/ pai metering 等（后三项 v0.8.1 起）；**v0.18.0 起存量 admin-only 命令收拢进 `trisol admin` 命名空间**（cluster 管理类、monitor、direct-access、storage trash、quota sync、inference short-domain 等），旧写法过渡期内仍可用并会给出去处提示 | **平台管理员** |
| `user` | 用户搜索 / 管理 | 搜索需团队或平台管理员；用户管理仅平台管理员 |

### v0.13.0：批量成员管理与 GPU 规格

```bash
trisol team add-members <team> <user>... [--role member|admin] [-o json]
trisol team set-role <team> <member|admin> <user>... [-o json]
trisol team remove-member <team> <user>... [-o json]
trisol cluster gpu-options --team <team> --cluster <cluster> --workload training|inference -o json
```

- 成员批量操作要求团队管理员权限；每个用户分别返回结果，部分失败不会回滚已成功项。重复执行是安全的。
- 角色变更和移除若会让团队失去最后一名管理员，会在执行前整体拒绝。
- `gpu-options` 返回当前 workload 可用的 GPU 规格（**v0.25.0 起该命令已废弃**，改用 `trisol quota list`，见下文 v0.25.0 节）；从 **v0.16.0** 起，提交训练或推理时使用返回的 `gpu_model` / CLI 参数 `--gpu-model`（产品名称）；旧的 `gpu_product_id` / `--gpu-product-id` 已移除。

### v0.14.0：调度置顶、成员配额与列表契约

```bash
trisol team list [--all]                           # 默认只列已加入的团队
trisol train list --gpu-model <机型> [--all]       # 推理 inference list 同
trisol team scheduling pin|unpin|pins <team> ...   # 详见下节
```

- `team list` 默认只展示你已加入的团队；`--all` 恢复全量视图（管理员发现其他团队的入口）。
- 训练 / 推理列表支持 `--gpu-model` 按机型过滤；`--all` 保证拉取全量（JSON 输出看 `has_more` 字段）。
- 调度新增排队任务手动置顶（pin / unpin / pins）与成员级 GPU 配额（member_cap），详见下节。

### v0.19.0：推理更新免重启与资源归属边界

```bash
trisol inference update <svc> --replicas 9            # 原地改副本，不重启实例
trisol inference update <svc> --public-access --auth-mode trisol
trisol inference update <svc> --lb-policy least_request
```

- **推理更新按集群类型自动选执行方式**：K8s 集群改副本数 / 公网访问 / 鉴权 / 负载均衡策略原地生效、秒级完成、不重启实例；PAI 集群运行中调副本走原生原地伸缩。更新涉及集群不支持的字段时，成功返回并列出「已忽略字段」及原因。
- **资源归属边界**：资源的更新 / 停止 / 删除只对创建者本人开放，操作他人资源返回 `403 RBAC_OWNER_REQUIRED`；管理员须显式加 `--as-admin`。
- `trisol team create`：修复组织管理员被误拦 403——组织管理员可直接创建团队（落在本组织），平台管理员仍用 `--as-admin`。

### v0.20.0：推理部署排障增强与 JSON 输出收敛

```bash
trisol inference create ... --failure-retention 48h      # 部署卡在失败证据超 48h → 判 failed 并自动释放（停计费）
trisol inference update <svc> --failure-retention never  # 恢复为「不限」（默认）
trisol inference get <svc> -o json                       # .deploy_state 查看部署中子状态与释放倒计时
```

- **`--failure-retention <时长>`**（create / update 均有）：部署卡在失败证据（镜像拉取失败 / 持续重启 / 配置错误）超过该时长，版本自动判 failed 并释放工作负载、停止计费；`0` / `never` / `off` = 不限（默认）。合法区间 10m–720h，越界返回 400。完整语义见 2.7「部署失败保留时间」。
- **部署中子状态直出**：`inference get <svc> -o json` 新增 `deploy_state` 块（仅版本处于部署中且存在投影时出现）：`substate`（`queueing` / `pulling` / `starting` / `image_error` / `restart_error` / `config_error`）、`summary`（各类实例计数）、`failure_retention`（`armed` / `since` / `deadline_at` / `remaining_sec` / `evidence`；倒计时以 `deadline_at` 为准在本地跳秒）。`inference list` 的 STATUS 列同步追加失败标记与 `auto-release in Xh`。
- **JSON / YAML 输出收敛（重要变更）**：用户面 `trisol inference` 命令（get / list / status / create / update / start / stop / revisions / rollback / canary 等，含 `--wait` 的最终输出）的 `-o json` / `-o yaml` 不再包含内部字段 `gpu_product_id` / `gpu_product_deleted`；`gpu_model` / `gpu_display_name` 保留。有脚本依赖这两个字段的，改用 `gpu_display_name`。
- **更新响应补齐 GPU 显示名**：`inference update` 等写操作的响应现在与查询接口一样正常返回 `gpu_display_name`（此前为 null）。
- **修复：管理员生命周期写不再被误拦**：管理员用 CLI 对团队 / 组织资源做生命周期写（`train stop/delete/update`、`inference stop/start/delete/update`）时，此前可能在解析阶段就被 403 误拦；现在先按普通身份执行，仅在管理员身份确实可能改变结果时才以 `--as-admin` 身份自动重试一次，管理员身份答不上的错误按原样透出。`--as-admin` 的使用方式不变。

### v0.21.0：多机分布式推理（--nodes）

```bash
trisol inference create ... --gpu-count 8 --nodes 2   # 单实例跨 2 台整机（16 卡/实例）
trisol inference update <svc> --nodes 2               # 更新为双机实例
trisol inference get <svc> --spec -o json             # .resources.nodes 回读实际生效值
```

- **`--nodes <N>`**（create / update 均有）：声明单个实例占用的整节点数，总卡数 = 每节点卡数 × 节点数 × 副本数。`--nodes > 1` 时 `--gpu-count` 必须等于所选规格的整节点卡数；与 canary / autoscale 互斥。
- **开放范围**：本期仅 PAI（灵骏）集群；其余集群类型提交返回 422 `provider_capability_unavailable`。
- **混布防护**：声明 `--nodes` 的提交后 CLI 回读持久化 spec 核对，字段未生效会明确报错（不会「以为多机实际单机」）。

### v0.22.0：GPU 命名口径统一与 member-cap 型号匹配修复

```bash
trisol team scheduling set <team> --member-cap-type per_model --member-cap 4 \
  --member-cap-model-override "NVIDIA A800-SXM4-80GB=8"   # 卡型按配额列表 GPU SPEC 列的拼写
trisol team scheduling get <team> -o json                  # 回显归一后的拼写
```

- **GPU 命名对外统一为 `gpu_model` 单一口径（产品名拼写）**：训练 / 推理 / 监控等命令的 JSON / YAML 输出自本版起不再返回 `gpu_display_name`（v0.20.0 节「`gpu_model` / `gpu_display_name` 保留」的表述随之过时——`gpu_display_name` 现已一并移除）；依赖该字段的脚本改用 `gpu_model`，其取值始终为产品名拼写（如 `NVIDIA A100-SXM4-80GB`）。
- **成员配额卡型例外按展示拼写匹配**：`--member-cap-model-override` 与 `--member-cap-override` 的 `@gpu_model` 按配额列表 GPU SPEC 列的产品名拼写匹配（产品名含空格时给参数值加引号）；旧技术拼写由服务端自动归一（未识别拼写原样保留、该卡型接入后生效），保存后 `team scheduling get` 回显归一结果。存量策略已随本版完成回填归一。

### v0.25.0：推理路由策略（--routing-policy）与规格可用性判断（quota list）

```bash
trisol inference create ... --replicas 4 --routing-policy cache_aware   # 多副本（≥2）sglang HTTP 服务可开
trisol inference update <svc> --routing-policy round_robin               # 回到默认策略
trisol quota list --cluster <cluster>                                    # 选规格：只有 STATUS=ready 的行可提交
```

- **推理服务新增路由策略 `--routing-policy`（create / update 均可指定）**：`round_robin`（默认，不传即是）或 `cache_aware`。`cache_aware` 面向多副本（≥2）sglang HTTP 服务：开启后正式流量（stable）经 cache-aware router 分发，同前缀请求落到同一副本，前缀缓存命中率显著提升（多轮对话等长前缀场景收益明显）。仅 K8s 集群可用（PAI / MLP 由 provider 管理流量，会拒绝该 flag）；与显式非默认 `--lb-policy` 互斥。提交后 CLI 会回读持久化 spec 核对，策略未生效会明确报错（不会「以为开了实际没开」）。
- **规格可用性统一看 `trisol quota list` 的 `STATUS` / `REASON` 列**：只有 `STATUS=ready` 的行可以提交；`syncing` 表示平台仍在同步，提交可能还进不去；`unavailable` 表示当前不可用，原因见 `REASON` 列（如 `quota_deleting`、`resource_not_ready`、`gpu_product_not_bound`）。选规格时取 `GPU SPEC` 列的产品名拼写传给 `--gpu-model`；可用 `--cluster` 过滤集群。GPU COUNT 显示 `N (pool)` 的是共享池总量（全组织共用的动态上限），不是你团队的专属配额。
- **`trisol cluster gpu-options` 已废弃（deprecated）**：同样的可用性信号已由 `quota list` 的 STATUS/REASON 列承载——迁移就是把 `gpu-options` 换成 `trisol quota list`（用 `--cluster` 过滤）。宽限期内旧命令仍可使用（运行时会打印迁移提示），新脚本请直接写 `quota list`。

`quota list` 的输出形如：

```text
ID                  TEAM     CLUSTER      GPU SPEC              GPU COUNT  STATUS       REASON                 UPDATED
1982904471162888192 my-team  ve-gpu-prod  NVIDIA L20            16         ready        -                      2026-10-10 12:00
1982904471162888193 my-team  ve-gpu-prod  NVIDIA H20            8          syncing      -                      2026-10-10 11:58
1982904471162888194 my-team  ve-gpu-prod  NVIDIA A800-SXM4-80GB 32 (pool)  ready        -                      2026-10-10 11:55
1982904471162888195 my-team  ve-gpu-prod  NVIDIA L20            8          unavailable  gpu_product_not_bound  2026-10-10 11:50
```

几个通用约定（记住能少踩坑）：

- **`-o json` 到处可用**：机器可读数据走 stdout，进度 / 日志走 stderr。脚本 / agent 优先 `-o json`。
- **`--all-teams`**：`quota / inference / model / dataset / train` 的 `list` 可加，一条命令列出**你所属全部 team** 的资源，不用切 team。与 `--team` 互斥。
- **name 解析**：大多 `get` / `download` 支持 `<name>` 或 `<name>:<version>`；省略版本一般取 **latest ready** 版本。
- **不可逆操作**（delete / stop）agent 一律带 `--yes` 跳确认。
- **计费写幂等**（v0.6.0 起）：`train submit` / `inference create` 等计费写操作，CLI 在首个网络请求前向 stderr 打印 `Idempotency-Key`。网络结果不明或返回 HTTP 202 时，用 `--idempotency-key <同一个 uuid>` 重放**同一意图**——不要换新 key、不要改 flag。

### v0.30.0：推理引擎指标与成员配额上限放宽

- **推理资源序列新增引擎自报告指标**：`trisol inference resources <service-id> --metric` 新增三个取值——`cache_hit_rate`（prefix cache 命中率，percentunit）、`input_tpm` / `output_tpm`（输入 / 输出 token 吞吐，tpm）。仅 catalog 托管 sglang / vLLM 服务提供；其余引擎与自定义镜像服务返回 422 `metric_unavailable`；本功能上线前创建的服务下次部署/更新后出数（此前为空序列）。Web 侧同口径数据在推理详情「流量」tab（见 2.7）。
- **成员（GPU 配额）上限放宽**：`trisol team scheduling set` 的 `--member-cap` 族 flag（含 `--member-cap-override` / `--member-cap-model-override`）值域上限从 1024 放宽到 2147483647（约等于不设限）；存量配置不受影响，无需迁移。

## 团队调度策略（CLI 配置，v0.10.0 起）

独享算力池默认全员**争抢**（shared）；团队可切换为**权重优先级**（weighted）——按成员层级给**等待中**的任务设可并发 GPU 上限，高层级先准入、低层级排队。优先级变更**异步生效**，运行中 / 已预留任务不受影响。Web 表单路径见「2.3 算力与配额」（团队详情「调度策略」页签，表单自动拼装规则，无格式坑）；本节是 **CLI 路径**——直接提交 policy.json，适合脚本与 agent。`set` 需团队管理员 / home-org 管理员 / 平台管理员；成员可读自己的记录。

```json
{"mode":"weighted","rule":"linear","linear":{"highest_priority_max_gpus":4,"gpus_per_level":4},"demand_scope":"per_quota"}
```

- `mode`：`shared`（默认争抢；恢复用 `set --shared`）或 `weighted`。
- `rule`：`linear`（线性递减）或自定义区间（`ranges`，形如 `[{"up_to_gpus":8,"priority":8}]`）。档位 1-8（8 最高），9 为 pin 专用档（v0.14.0 起，见本节末）。
- `linear` 两字段**必须同时显式给出**：最高档并发上限与逐档步长（Web 编辑器默认 8/4）。
- `demand_scope`：需求计价口径，仅 weighted 可带——`team_global`（默认：按成员**全团队**已占 GPU 计）或 `per_quota`（只计所选池）。`set --demand-scope` 可覆盖文件值。

```bash
trisol team scheduling get <team> -o json                        # 读当前策略 + ETag
trisol team scheduling preview <team> --quota <QUOTA_ID> --policy-file policy.json \
  --occupied-gpus 0 --queued-gpus 8 --tasks 4 --gpus-per-task 1   # 后端干跑，不落库
trisol team scheduling set <team> --policy-file policy.json      # 保存（默认先读 ETag）
trisol team scheduling set <team> --shared                      # 恢复争抢制
trisol team scheduling status <team> --quota <QUOTA_ID> -o json  # 落地与等待梯队
trisol team scheduling history <team> --limit 20                 # 变更历史
```

- `preview` 不带 `--policy-file` 时预演**已保存**的策略；`--occupied-gpus` / `--queued-gpus` 手动基线不给则用成员观测需求。
- **409 = 策略已被他人改过**：重新 `get` 拿新 ETag 再 `set`，CLI 不自动重试；`--etag=` 仅限首次创建。
- `status` 的 **DEMAND CALC** 列 = 已预留 + 前序等待 + 本任务申请（同快照可直接加和核对）；`team_global` 口径下出现 `DEGRADED` 融合态 = 权重暂停生效，属预期而非故障。
- 独享配额 `synced` 但队列缺失时不可用——属配额恢复流程（平台管理员），与调度策略无关。

### 手动置顶（pin）与成员配额（v0.14.0 起）

```bash
trisol team scheduling pin <team> --quota <QUOTA_ID> --workload-uid <UID> --priority 9
trisol team scheduling unpin <team> --quota <QUOTA_ID> --workload-uid <UID>
trisol team scheduling pins <team>                # pin / unpin 审计记录
```

- **手动 pin**：把排队中（waiting）的任务钉到固定优先级档（1-9，9 为 pin 专用档）。仅 weighted 模式可用；异步生效（调度 worker 下一轮写入原生优先级），任务被准入后 pin 自动失效；运行中 / 已结束任务不可 pin。需团队管理员。
- **成员配额（member_cap）**：policy.json 里的可选块，限制单个成员在团队内的 GPU 并发上限，超限的新提交会被拒绝。与调度排序正交，shared / weighted 都可配置；不配置 = 不限制。

## Agent Skill：冷启动链路

Agent Skill 是一篇 **冷启动编排 playbook**，覆盖几条「从零到可用」链路 + 一条端到端：

| 链路 | 形态 | 断点 |
|-|-|-|
| 导入 / 上传 model | 本地上传（≤ 200 GiB）；HF `model import-hf [--precache] --wait`（总量 ≤ 1 TiB、单文件 ≤ 42 GiB）；外部 S3/OSS 导入（≤ 1 TiB） | 全部 `--wait`，连贯 |
| 数据集（文渊管理） | 数据集的上传 / 浏览 / 下载都在**文渊（wenyon）**进行，不在 trisol 侧操作 —— trisol 侧误触发写 / 下载时，错误体自带文渊引导（安装 / 登录 / 控制台入口），命令见 `wenyon-cli --help` | N/A |
| 部署 inference | 解析 code + source + quota 行 → `inference create --model NAME:CODE --cluster [--gpu-model] [--gpu-count] --wait` | 连贯 |
| 提交 training（SFT） | 解析 base + dataset `NAME:CODE`（文渊数据集：NAME = 文渊卡片 ID，CODE = 整数版本号，如 v1 → 1；`wenyon-cli dataset versions <id>` 查版本；**不要**加 `wenyon:` 前缀）+ quota 行 → `train submit` → job_id | **fire-and-forget**，续接 / 自动化用 `train wait` |
| **train-to-serve** | data + base → 训练 → 上线 | 仅训练一个硬断点 |

**什么时候用 skill**：冷启动（第一次、不知道 version / cluster / gpu）、多步编排、train-to-serve。  
**什么时候直接用 CLI**：已有全部 ID 的单命令快乐路径、day-2 运维（调参 / canary / 配额管理 / 浏览）。

Skill 的核心价值 = **解析逻辑**，把「人肉查 code」吃掉：

- **name → 版本号**：`model get <name> -o json` 里挑 `versions[] | select(.status=="ready") | max_by(.version_code)`；别用 `latest_version_code`（它不看 status，可能指向 importing / failed 的版本）。
- **cluster + gpu_model**：`quota list --all-teams -o json` 一行 = 一个 (team, cluster, gpu_model) 分配，整行选，别混搭。

每条链路都是「**发现 → 执行**」两阶段：发现阶段只读 `-o json` 拿环境事实（quota 行 / 版本状态），解析决策后，把值填进真正的写命令执行。

> **训练是唯一硬断点**：`train submit` 后**不阻塞**，拿到 `job_id` 就结束本轮。续接或自动化用 `trisol train wait <job_id>` 阻塞到终态；成功且声明了输出模型时读 `output_model_version_code` + `output_model_id` + `mode`，再 `model get` 拿 name（部署要 **NAME:CODE**，不是 id），用**精确 version_code**（不是 latest）部署。

## 下载模型 / 数据集

**model — `trisol model download <name>[:<version>] [-o <dir>]`**

- **整版下载**：不带位置参数，用 `-o <dir>` 选目标目录（默认 `./<name>-<version>/`）。缓存路由（S3 / 集群预热 / `--direct-hf`）自动。
- **位置参数坑**：第 2 个位置参数是 **repo 内文件路径（单文件下载），不是**本地目标目录。`model download <name> ./out/` 会被当成找 repo 里叫 `out/` 的文件 → 找不到。整版到目录用 `-o`，别用位置参数。
- **adapter 决策**：下载前先 `trisol model get <name> -o json` 看目标版本有没有 `adapter` 字段：

  - **有** → 是 LoRA / QLoRA adapter，`download` 只会拿到 adapter 权重（`adapter_config.json` + `adapter_model.safetensors`，不含 base）。本地要跑 / merge 的话，还要按 `adapter.base_model_name:adapter.base_model_version_code` 另下 base。
  - **无** → 普通整模型，直接下。

**dataset —— 已统一到文渊**

`trisol dataset download` 已废止（400 `dataset_download_abolished`，错误体自带文渊引导四件套）：数据集字节下载统一到文渊 —— 按引导到文渊控制台操作，或用 `wenyon-cli`（`wenyon-cli dataset download`，详见 `wenyon-cli --help`）。

## 常见问题

- **认证报 PAT 相关错误**（`pat_removed` / 本地提示 PAT 已移除）→ PAT 已于 v0.6.0 删除。`TRISOL_TOKEN` 或旧凭据文件里的 `trp_...` 清掉，人工跑 `trisol login`（device code 可无浏览器），CI 改用 mint 的短期 Vouch JWT。
- **命令 / flag 报 `unknown command` / `unknown flag`，或 `-o json` 里依赖的字段缺了** → skill 可能比 CLI 旧了。`trisol skill update` 后重试（可先 `trisol skill list` 看状态）。
- **`quota list` 非管理员返空 / 403** → 没设激活 team，掉到管理员端点了。设激活 team（`trisol config use-team <name>`）或加 `--all-teams`。
- **部署报 `runtime.image: required`** → 该模型来源（import / upload / 自定义训练产物）推不出运行时，得提供镜像 —— 优先 `--image-ref`（公司镜像中心 catalog 引用，用 `trisol image list` 查 `full_path`）；`--image` 字面地址仍可用作逃生口，但已 deprecated。HF / llama-factory full | lora 产物则一键无需 image。
- **训练数据集不可训练** → `train submit` 前确认 `manifest.trainable`（不是 `status`）：懒加载 HF 数据集可能 ready 但不可训。
- **LoRA 部署 422** → base + adapter serving 要集群有 active PFS；选 quota 行时优先 PFS 集群。
- **数据集写 / 下载报 `legacy_dataset_frozen` / `dataset_download_abolished`** → 数据集已归属文渊：写操作与字节下载都在文渊做，错误体自带安装 / 登录 / 控制台引导，按指引走即可。

> 命令真值以 `trisol <cmd> --help` 为准；本页随 CLI 演进更新。



## 资源池命令（v0.33.0）

Bohr 用户将下列命令中的 `trisol` 换成 `bohr trisol`。

### 组织管理员：发现、关联与调序

```bash
trisol team pool associable
trisol team pool list
trisol team pool associate --cluster <集群ID> --pool <池ID>
trisol team pool unassociate --cluster <集群ID> --pool <池ID>

trisol team pool order --cluster <集群ID>
trisol team pool order --cluster <集群ID> --set <id1,id2,...>
trisol team pool order --pool <池ID> --first
```

- `associable` 列出本组织当前可关联的池，`list` 查看当前团队已关联的池。
- `order` 不带写参数时读取顺序；独享始终第 0 位。`--set` 一次保存完整目标顺序。
- 单池移动可用 `--first`、`--last`、`--before <池ID>`、`--after <池ID>`；池 ID 可自动反解集群。
- 调序并发冲突返回 `rank_conflict` 时，先重读当前顺序再保存。
- 关联与调序异步生效，等待数秒后再提交任务。多池团队解除关联时必须指定 `--pool`。

### 平台管理员：池与容量

```bash
trisol admin compute pool create-whitelist --name <名称> --cluster <集群ID>
trisol admin compute pool create-public --name <名称> --cluster <集群ID>
trisol admin compute pool bind <池ID> --org <组织>
trisol admin compute pool unbind <池ID> --org <组织>
trisol admin compute pool list-bindings <池ID>

trisol admin compute pool-quota allocate --cluster <集群ID> --resource-id <真实资源ID> --gpu-count <数量> --pool-id <池ID>
```

公共开放池使用 `public-detach <池ID> --org <组织>` 剥离组织，使用 `list-public-detach <池ID>` 查看剥离清单。组织没有其他消费来源时，服务端拒绝剥离。

默认公共通道晋升使用：

```bash
trisol admin compute pool promote-public <池ID> --cluster <集群ID>
trisol admin compute pool promote-public <池ID> --cluster <集群ID> --confirm
```

第一条是零写预演，第二条才切换默认指针并播种团队关联；目前仅支持 K8s 域。PAI 遥测端点通过 `trisol admin compute domain update <域ID> --telemetry-prometheus-endpoint <地址>` 设置，使用 `--clear-telemetry-prometheus-endpoint` 清除。

完整概念与消费顺序见 [2.3 算力与配额](https://dptechnology.feishu.cn/wiki/A8lowPReMiItIIkJAC8cP5ZTncb)。
